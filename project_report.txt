1. Introduction
Personaliz AI Assistant is a desktop automation assistant built with Tauri, React, and Rust, with Python automation support. The project provides a no-code conversational interface to create and run automation agents (especially LinkedIn-focused workflows), schedule them, review outputs, and maintain logs. The system is designed around local-first execution and combines local AI (Llama3 via Ollama) with optional external LLMs.

The repository implementation shows a multi-layer architecture:
- Desktop UI in TypeScript + React (`src/`)
- Native/backend command layer in Rust (`src-tauri/src/main.rs`, `src-tauri/src/db.rs`, `src-tauri/src/scheduler.rs`)
- Automation engine in Python (`public/agent_engine.py`)
- Optional broker service for remote control in Python/FastAPI (`broker/main.py`)

1.1 Scope of the System
Scope includes:
- Desktop onboarding for AI/automation setup (Ollama/llama.cpp/OpenClaw/API keys)
- Chat-based assistant to guide setup and operations
- Agent creation and management (name/role/goal/tools/schedule)
- Scheduler support for hourly/daily/weekly/custom cron runs
- LinkedIn automation (post generation + hashtag commenting)
- Human-in-the-loop approval before production posting
- Local SQLite persistence for agents, schedules, logs, run history, approvals, and OpenClaw runs
- Integration with local LLM (Llama3) and optional cloud LLM providers

Out of scope in current implementation:
- Multi-user enterprise identity/access management
- Distributed job queue with durable cloud database (broker is MVP/in-memory)
- Advanced analytics dashboards

1.2 Existing System
Traditional automation systems usually require:
- CLI-driven setup and JSON/YAML editing
- Separate tools for scheduling, LLM calls, and browser automation
- More technical skills for non-programmers

Typical standalone existing approaches:
- Manual social posting
- Basic scripts without scheduler/audit trail
- Generic cloud automation with less local privacy control

1.3 Problems in Existing System
Common issues in existing/manual approaches:
- High setup complexity for non-technical users
- No unified UI for creating, scheduling, and monitoring agent workflows
- Weak local auditability of model usage and approvals
- Limited human review workflow before publishing external content
- Less privacy in cloud-only AI solutions

1.4 Features of Proposed System.
Implemented features from this repository:
- Tauri desktop app with chat, agents, logs, settings tabs (`src/App.tsx`)
- 5-step onboarding wizard (`src/components/Onboarding.tsx`)
- 4-step agent creation modal with live cron validation (`src/components/AgentCreationModal.tsx`)
- Approval modal and approval audit logging (`src/components/ApprovalModal.tsx`, `db_record_approval`)
- Local AI support using Ollama and llama.cpp endpoint checks
- External LLM routing (OpenAI/Anthropic/Google) in Rust command layer (`send_message_to_external_llm`)
- Python Playwright automation for LinkedIn posting/commenting (`public/agent_engine.py`)
- SQLite persistence and scheduler orchestration (`src-tauri/src/db.rs`, `src-tauri/src/scheduler.rs`)
- Optional remote broker MVP via FastAPI + WebSocket (`broker/main.py`)

1.5 Benefits of Proposed System.
- Local-first privacy: keys and operational state are stored locally
- Better usability: non-technical users can operate through guided UI and chat
- Reliability: scheduler + logs + run history + approvals create operational traceability
- Flexibility: supports both local LLM (Llama3/Ollama) and cloud LLMs
- Safety: sandbox mode and approval flow reduce accidental production actions

2. Analysis
2.1 System Requirement Specification (SRS).
Functional requirements:
- FR1: User can complete onboarding for local LLM/OpenClaw/API keys
- FR2: User can create/edit/delete agents with schedule and tools
- FR3: System validates custom cron expressions and computes next run
- FR4: System can execute automation via Python engine and OpenClaw CLI
- FR5: User can approve/reject generated content before production posting
- FR6: System stores agent metadata, logs, run history, LLM usage, approvals, OpenClaw run outputs
- FR7: User can query logs, run history, and approvals in the UI
- FR8: System can send chat prompts to local or external LLM

Non-functional requirements:
- NFR1: Desktop responsiveness for agent operations and log viewing
- NFR2: Local data persistence in SQLite for offline continuity
- NFR3: Security through local key handling + explicit approval flow
- NFR4: Maintainability via modular frontend/backend/automation separation
- NFR5: Cross-platform target through Tauri stack

2.2 Resource Estimation and Cost Estimation
Development resources:
- Frontend developer skills: React + TypeScript + CSS
- Backend/native integration skills: Rust + Tauri
- Automation scripting skills: Python + Playwright
- Optional broker deployment skills: FastAPI/WebSockets

Runtime resource estimate (single-user desktop):
- CPU: modern 4-core or better
- RAM: 8 GB minimum (16 GB recommended for local Llama3)
- Disk: model storage for Ollama (Llama3 can require multiple GB) + app data/logs
- Network: required for LinkedIn automation and cloud LLM APIs

Cost estimate (project/student use):
- Local execution cost: low (desktop compute + electricity)
- Cloud LLM API cost: variable by usage/model if external APIs are enabled
- Broker hosting (optional): low-tier cloud service for MVP

3. System Design.
3.1 Architecture of a system
The system uses a layered desktop architecture:

Component Architecture Diagram (ASCII)

[User]
  |
  v
[React + TypeScript UI (src/App.tsx, components/*)]
  |  invoke() via Tauri bridge
  v
[Rust Tauri Command Layer (src-tauri/src/main.rs)]
  |\
  | \---> [SQLite Layer (src-tauri/src/db.rs)] ---> data.db (local file)
  | \
  |  \--> [Scheduler (src-tauri/src/scheduler.rs)]
  |   \
  |    \-> [Python Agent Engine (public/agent_engine.py)] ---> [Playwright/LinkedIn]
  |
  \-----> [LLM Integrations]
           |- Local: Ollama / llama.cpp
           \- External: OpenAI / Anthropic / Google APIs

Optional remote control path:
[Desktop App] <WebSocket> [Broker FastAPI Service (broker/main.py)] <WebSocket> [Client UI]

Sequence Diagram 1: Chat to LLM
User -> UI: Enter message
UI -> Rust command: send_message_to_llm / send_message_to_external_llm
Rust -> LLM endpoint: HTTP request (local/cloud)
LLM endpoint -> Rust: generated text
Rust -> SQLite: log model usage (llm_usage)
Rust -> UI: response
UI -> User: render assistant reply

Sequence Diagram 2: Scheduled Agent Execution
Scheduler loop -> SQLite: read enabled schedules
Scheduler -> Scheduler: compare now vs next_run
Scheduler -> Python engine: execute due agent
Python engine -> LinkedIn/automation target: perform/simulate actions
Python engine -> Scheduler: JSON result
Scheduler -> SQLite: update run_history/logs/schedule next_run
UI -> SQLite: fetch logs/history for display

3.2 SDLC Model Used
Recommended model reflected by repository evolution: Iterative/Incremental SDLC.
- Iteration 1: Core desktop shell and chat
- Iteration 2: Agent CRUD + scheduling + DB persistence
- Iteration 3: LinkedIn automation + approval workflow
- Iteration 4: External provider integrations + broker MVP

Why suitable:
- Feature-wise modularity allows staged delivery
- Supports frequent validation in an integration-heavy project

[User] <--> (Personaliz AI Assistant System) <--> [Local LLM / External LLM APIs]

P2: LLM Orchestration

  Outputs: generated response, llm_usage records

P3: Agent Management & Scheduling
  Inputs: agent definitions, schedule rules
  Outputs: run triggers, next_run updates, run status

P4: Automation Execution Engine
  Inputs: agent commands/content/sandbox flag
  Outputs: action results, execution logs

P5: Persistence & Audit
  Inputs: events from all processes
  Outputs: stored agents/schedules/logs/history/approvals/openclaw_runs

Data stores:
- D1: SQLite `data.db`
- D2: Local browser profile and app state files

3.6 E-R Diagram.
Since the project uses SQLite, ER modeling is directly applicable.

ER Diagram (conceptual text)

[AGENTS] 1 ----- N [SCHEDULES]
[AGENTS] 1 ----- N [LOGS]
[AGENTS] 1 ----- N [RUN_HISTORY]
[AGENTS] 1 ----- N [APPROVALS]
[AGENTS] 1 ----- N [OPENCLAW_RUNS]
[LLM_USAGE] is independent event log (not strictly FK-bound to AGENTS)

Entity notes:
- AGENTS is the core entity (id as primary key)
- SCHEDULES references AGENTS via `agent_id` (with cascade delete)
- Operational/audit entities capture lifecycle and governance data

3) logs

5) llm_usage

- id (PK, INTEGER AUTOINCREMENT)

4. System Implementation.
4.1 Functional module Description.
Module A: Desktop UI and Interaction
- Main file: `src/App.tsx`
- Handles tabs, chat flow, agent list, logs/history rendering, settings, and command dispatch.

Module B: Onboarding and Setup
- `src/components/Onboarding.tsx`
- Multi-step setup for local model backend, OpenClaw install checks, API key capture.

Module C: Agent Configuration and Approval
- `src/components/AgentCreationModal.tsx`
- `src/components/ApprovalModal.tsx`
- Creates agent metadata and validates cron; enforces review step for production posting workflows.

Module D: Native Command/API Layer
- `src-tauri/src/main.rs`
- Exposes Tauri commands for LLM messaging, dependency checks, DB CRUD, scheduling, and automation execution.

Module E: Scheduler and Cron Engine
- `src-tauri/src/scheduler.rs`
- Polls schedules, computes due jobs, parses cron expression, triggers execution, and records outcomes.

Module F: Persistence Layer
- `src-tauri/src/db.rs`
- Initializes schema, performs DB operations for all app entities, supports log and audit retrieval.

Module G: Python Automation Engine
- `public/agent_engine.py`
- Provides CLI/subcommands for LinkedIn posting/commenting/trending topics.
- Includes local Ollama generation path (`llama3:8b` default), post validation/cleanup, and sandbox behavior.

Module H: Optional Remote Broker
- `broker/main.py`
- FastAPI endpoints + WebSocket channels for task dispatch and device status updates.
